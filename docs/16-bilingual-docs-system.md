# 16 · 双语文档系统：blob 哈希配对、自研 merge driver、术语表治理

> 研究对象：deepseek-harness @ `47f9438`。依据：`docs/i18n/README.md`（60 行契约）、`translation-rules.md`、`terminology.md`（214 行术语表）。全仓库每篇在册文档（含全部 683 篇 Agent Note）都是中英双语维护的——这套让它可持续的机制本身就是一个值得研究的工程系统。

## 配对契约：三个兄弟文件

一对文档 = `foo.md` + `foo.zh.md` + `foo.i18n.yaml`（一致性记录），同目录、**整对合并**——PR 永不允许只落一种语言。没有 locale 目录、没有独立翻译仓库、没有混排双语文件。

**两种语言权威平等**：文档可以中文先写（"中文先行的 Agent Note 与英文先行的同等合法"），对侧从它翻译。绑定两者的不是主从关系，而是"必须说同一件事"。

## 一致性记录：为什么是 blob 哈希

```yaml
foo.md: 3f786850e387...
foo.zh.md: 89e6c98d9288...
```

记录的是两侧**上次被确认一致时**的 git blob 哈希。三个设计细节层层递进：

1. **blob 哈希而非 commit 哈希**——同一 PR 内编辑的文件也能算（`git hash-object`），一致性成为纯内容比较
2. **`--write` 先把快照存进本地 Git 对象库**，并把每个 blob 钉在内容寻址的 `refs/dsh/translation-pairing/snapshots/` ref 下——**GC 无法使记录的恢复指针失效**
3. 于是失配的修复方式被结构性地引导为**最小补丁**：从记录哈希恢复"上次确认的精确文本"，对着被编辑侧的 diff 给对侧打最小补丁——"永不整篇重译"

重录哈希的 yaml diff 就是"确认一致"这个动作本身的可评审载体，所以 `--write` 必须点名你确认过的 pair（`--write --all` 是显式的全库形式）。

## 自研 git merge driver：fail-closed 的自动合并

两个分支各自合法确认了同一 pair 时，安装的 `dsh-translation-pairing` merge driver 只在满足全部条件时才合成新记录：Git 默认文本合并对两侧记录的 owner-blob 三元组都成功、合并后的 pair 保住必需的语言切换链接与结构签名。**任何 driver 无法验证的结构都保持普通冲突**；`resolve-translation-pairing-conflicts` 对已停止的合并做同样的 fail-closed 操作。（我们在 04 篇跑通仓库时正是被 `pnpm install` 自动装上了这个 merge driver。）

## 结构签名：机器管形，评审管义

门禁机械检查的"结构签名"：标题深度与顺序、列表种类、有序列表起始值、列表项数、表格行列数、链接目标（除切换链接外）、**代码块逐字节一致（含注释）**。中文文件的 `ts` 代码块被当作英文侧的**派生物**消费——字节一致就不用编译两次。

而门禁的边界声明得极其诚实：

> **门禁绿 = 这对内容在此刻被确认过一致，不 = 确认本身是可靠的。** 它查哈希与 Markdown 结构，无法判断两侧是否真说同一件事、措辞是否准确得体——那是评审人的那半份契约。草率的对侧能过门禁；它不该过评审。

## 术语表与翻译规则：语言治理

`terminology.md` 是术语唯一权威，表结构含"不要译作"禁译列（如 Agent Note 禁译"智能体笔记"）与首现括注规则（`agent（智能体）` 首现括注、后续裸写；已在组合词里括注过的成员词不再重复括注）。

`translation-rules.md` 用 RFC 2119 等级（MUST/SHOULD/MAY）写翻译规则，几条见功力：

- **忠实**：对侧 MUST 说源侧说的话——不加不减行为/前提/警告/版本声明；"两侧实质不一致时，没有哪种语言默认获胜：改错的那侧，同一变更里把另一侧带上"
- **语态**：以 style-samples.md 的**人工批准金样对**校准文风（每种文档体裁一对），"样本与文风规则冲突时样本赢"；中文目标用机构技术中文、给句子显式主语（系统、门禁、评审人）、用地道工程语汇（误报/漏检）而非直译腔
- **段落边界可以不同**——结构签名故意不数段落，语义单元优先
- 翻译提示词模板本身是**可执行的**（`translation-prompt.ts` 渲染双向模板 + 解析三段式响应，`verify-translation-prompt` 在 doc-sync 里测两个方向）——连翻译流程的 prompt 都有门禁

## 观感

这套系统解决的是一个常被放弃的问题：双语技术文档在高速迭代下必然腐烂。他们的解法结构是"**把'一致'变成有记录、可恢复、可评审的状态**（blob 哈希 + 快照 ref + yaml diff 即确认动作），**把机器能查的形全部机查**（结构签名 + merge driver），**把机器查不了的义显式留给评审**（门禁边界声明）"。对任何维护多语言文档的项目——包括只有 README 中英双份的小仓库——三件套（sidecar 记录、最小补丁纪律、术语表禁译列）都能按比例缩小后直接用。
